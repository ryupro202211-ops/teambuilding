# マイベストライフ改修報告

## 1. 原因

人物・イベントの保存先は、既存のGoogle SheetsとApps Scriptだった。保存成功後に画面内の `DATA` / `EVENTS` は更新されるが、端末に最新状態を保存していなかった。リロード時は日次ビルド時点の埋め込みデータから始まり、API再取得が失敗すると古い表示が残った。サーバーに保存できていても、画面では変更が取り消されたように見える構造だった。

完了チェックには別の問題があった。旧マスターの `syncTaskState()` は `local[id] === true || remote[id] === true` で状態を合成していた。端末でチェックを外しても、サーバー側の古いチェックが復活する。解除操作の再送記録と、遅い応答への対策が必要だった。

## 2. 修正内容

人物・イベントは既存APIの保存成功後に内部データを更新し、端末へ暗号化して保存してから画面を更新する。起動時は公開データを復号した後、同じ日次データに対応する端末の保存内容を復元し、APIで最新状態を確認する。通信できない場合も端末の保存内容を表示できる。

完了チェックはチェック・解除の両方を未送信操作として記録する。タスクごとに送信順を保ち、古い取得応答が新しい操作を取り消さないようにする。既存の端末保存データは初回同期時に移行する。

JSON破損、復号失敗、型不正は公開データへのフォールバックで処理する。端末の容量不足などで保存できない場合は通知し、シートへの保存成功と端末への保存失敗を区別する。

## 4. 保存方式

Google Sheetsを正本として維持する。人物・イベントの端末キャッシュはPBKDF2・AES-GCMで暗号化し、localStorageへ保存する。連絡先の平文は端末にも公開ソースにも保存しない。別の日次世代のキャッシュは重ねない。

完了チェックは従来のApps Script `taskState` と端末保存を使う。送るのはタスクIDと完了フラグで、認証方式は変更しない。

## 5. 実施したテスト

- Nodeによる既存テストと保存・復元・分割公開の回帰テスト。
- 実際のChromiumで、初回表示、予定編集、保存後のオフラインリロード、人物追加、検索・並び替え、イベント削除、チェックと解除、ページを閉じて再開、保存JSON破損、スマホの分析表示を検証。
- 元画像6枚のバイト一致、公開ファイルのSHA-256、依存ファイル欠落、書き込み失敗、非公開素材の除外を検証。
- Windows公開スクリプトのASCII制約とPowerShell構文を検証。

本番の連絡先・イベントをテスト目的で変更していない。

## 6. テスト結果と性能

`npm test` は413件すべて成功。ChromiumのE2Eは10シナリオ成功。別のレビュー担当が見つけた重要3件（同期応答の競合、一括編集の競合、固定PCへのテスト依存）は、再現テストを失敗させてから修正し、全件を再確認した。GitHub ActionsでもWindows上で既存テスト・公開依存検証・架空データのE2Eがすべて成功した。[実行結果](https://github.com/ryupro202211-ops/teambuilding/actions/runs/36649013182)。英語環境で見つかったPowerShellの文字コード依存も再現して修正した。

改修は[ドラフトPR #1](https://github.com/ryupro202211-ops/teambuilding/pull/1)にまとめた。確認済みのコミットは `6b62b92fb943b6347a918644b453ffec54394737`。mainへの即時反映はしていない。

旧HTMLは8,281,764バイト。新HTMLは約9.5KBで、成果物全体は約6.31MB。画像は圧縮せず、Base64を元の画像ファイルに戻して約1.98MB削減した。ハッシュ付きファイルにより、変更していない画像・CSS・JSをブラウザで再利用できる。

架空データ・ローカルHTTP・Chromiumで1回ずつ測ったロード完了は旧332ms、新62ms。これは公開サイトの通信速度を保証する値ではない。復号後のDOM数は旧341、新350で、増加の主因は外部script等。初期表示のスクリーンショットは1280×1889で画素差0だった。JavaScript実行時間を単独で切り出した測定は行っていない。

## 7. 残っている課題

- ストレージが拒否・削除された端末では、再起動時にAPI通信が必要になる。保存失敗を画面で通知する。
- 古い日付のキャッシュを新しい公開データへ重ねないため、日次更新後の通信障害では最新のSheets変更を再取得できるまで公開時点の内容になる。
- イベントの空配列をAPI再取得で拒否する旧仕様は維持した。端末キャッシュの空配列は復元できる。
- 書き込み合言葉のlocalStorage保存と、固定の閲覧パスフレーズは既存仕様。共有端末や悪意あるスクリプトへの耐性を高めるには別途認証設計が必要。
- 今回の確認は架空データのローカル環境で行った。公開反映後の参照ファイル取得・ロック解除の確認は公開手順で行う。
- 古いハッシュ付き成果物は旧ページの参照を壊さないため保持する。長期運用では世代を指定した整理が必要になる。
- キャッシュ復元通知には保存時刻がなく、最新取得後も確認中の文言が残る。動作に影響しない表示上の改善として残した。
- mainへの即時反映はPRのレビュー後に行う。ローカルの編集元と日次公開処理は改修済みなので、次回の日次更新では新構成を公開する。

## 8. DB化の判断

今回の不具合を直すためにDBへ移す必要はない。既存Sheets・Apps Scriptと暗号化キャッシュで対応できる。複数人の同時編集、権限の分離、監査履歴、データ量の増加が必要になった段階で、認証付きAPIとDBへの移行を検討する。
