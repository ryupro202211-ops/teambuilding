### サイズと性能

- Base64画像：7,937,992バイト（HTMLの95.8％）。6枚に重複画像はなかった。
- 同じ画像の元ファイル合計：5,953,486バイト。外部化によりBase64分の約1.98MBを減らせる。
- 暗号化データのJSON：約151KB。巨大化の主因ではない。
- 画像を含むstyle内容：約7.99MB。script内容：約288KB（暗号文・イベント等を含む）。
- 画像埋め込みだけを取り除いたHTMLは計算上約344KB。CSS・JSも外部化するとさらに小さくなる。
- JSDOMでの静的HTML解析は今回の1回の計測で約1.98秒、静的DOMは140要素。通信・復号・描画を含む実ブラウザの初期ロード時間ではない。
- `render()` は一覧を毎回描画し、garden表示時には庭も描画する。非表示の一覧も更新するため、変更時に余分なDOM処理がある。
- 公開HTMLはインラインscriptが2本、外部scriptは0本。googleapisは日次取得用、jsdomはテスト用で、ブラウザへ読み込む不要なライブラリが巨大化の原因ではない。
- 実ブラウザの通信時間、復号時間、操作時の描画時間、描画後DOM数は実装時に同条件で改修前後を測定する。

## 問題点

### リロードで変更が戻るコード上の原因

1. `build.js` の `gateHtml()` は、リロードのたびに公開時点の暗号文を復号し `DATA=payload.contacts` を実行する。
2. `saveEdit()` / `saveProfile()` / 新規追加 / 一括編集はAPI成功後にメモリ内のDATAを更新するが、その結果の端末キャッシュを保存しない。
3. 復号後の `refreshRegisteredPeople()` は最新シートを読むが、トークンがなければ取得しない。通信失敗・応答不正・編集競合では公開時点のDATAを残す。
4. したがって、シートへの保存が成功していても、再取得できないリロードでは古い公開データを表示する。イベントにも同様の復元上の弱点がある。

架空データとAPIモックで、9/30の予定を10/3へ保存成功 → 新しいページインスタンスへリロード → 最新取得が通信失敗 → 9/30へ戻る、を再現した。保存後のlocalStorageには書き込み用合言葉だけが残っていた。

これは本番Google Sheetsの保存失敗を確認したという意味ではない。本番のGASデプロイ内容・通信結果・シートの実値は別途照合が必要。最新取得が正常なら現行コードもシートの変更を復元できる。

### 完了チェックの巻き戻り

`syncTaskState()` はlocalとremoteのtrueの和集合を採用する。チェック解除はlocalからキーを削除するため、解除のAPI送信が失敗・遅延した場合、古いremoteのtrueが解除を上書きする。架空タスクで、解除後に古いremoteを取得するとtrueへ戻ることを再現した。

`setLocalTaskDone()` のlocalStorage書き込みにtry/catchがなく、容量不足や保存禁止ではUI更新・同期まで到達しない。読み取り側の壊れたJSONへの対策は一部実装済みだが、保存失敗と未送信の解除は扱えていない。

### その他

- `_deploy_garden.ps1` はcomlist.htmlだけを公開するため、フロントの分割と同時に公開・検証処理の改修が必要。
- build.jsとテストにはインラインの宣言・描画位置を前提にした照合がある。タグだけ分割すると復号・差し込み・テストが壊れる。
- 手順書はイベント物理削除を禁止しているが、現行UIは完全削除を提供し、GASの `deleteEvent_()` は `deleteRow()` を呼ぶ。実装と文書が一致していない。今回これを勝手に削除・別動作へ変更しない。
- 行番号 `_row` は書き戻し先。古いキャッシュの行番号だけで書き込まず、既存の名前照合・行ズレ補正を維持する。
- イベント・空き枠は現状平文公開。個人名や非公開情報が入る場合は情報の公開範囲を見直す必要がある。
- 端末には認証情報が保存される。個人情報まで平文localStorageに追加する構成は採用しない。

## 改修方針

### 比較と推奨

1. **推奨：公開ファイルを分割し、Google Sheetsを正本として暗号化キャッシュを補助に使う。** HTMLとレビュー差分を小さくでき、再取得失敗でも直前の保存内容を復元できる。
2. ソースだけ分割し、公開時に単一HTMLへまとめる。現在の公開方式は維持しやすいが、8MB問題と公開コードの調査負担が残る。
3. DBと認証を新設する。競合や監査履歴には有利だが、今回の目的に対して変更範囲が大きい。

### 初期化と保存

- 初回：公開暗号文を検証して復号 → 検証済み端末キャッシュがあれば復元 → UI表示 → APIで最新状態へ同期。
- 端末キャッシュは公開世代・スキーマ版・取得日時を持つ。復号不能・JSON破損・型不正はキャッシュを採用せず、公開データへフォールバックして警告する。
- キャッシュはAES-GCMで暗号化し、復号鍵を平文データと一緒に保存しない。鍵の作成・破棄はロック解除のライフサイクルに合わせる。
- 公開世代とキャッシュ世代が異なる場合は、古いキャッシュを無条件に正本扱いしない。API成功時は全件置換して削除・空欄も反映する。通信失敗時のキャッシュ表示には基準日時と未同期状態を示す。
- 人物・イベント：操作 → API保存確認 → 内部状態更新 → 暗号化キャッシュ保存 → UI更新。API失敗を保存成功と表示しない。シート保存後に端末保存だけ失敗した場合は、それを区別して報告する。
- タスク：true/falseを持つ未送信操作を記録 → 内部状態とUIを更新 → 同期。APIが確認した操作だけ未送信状態を解除し、古い取得応答がその後の操作を上書きしないようにする。
- 別端末の変更はサーバー取得を優先し、未送信の自端末操作だけを重ねる。日付別の既存キーは移行して既存チェックを保持する。
- 入力途中と保存済みを区別する。今回は保存を完了した編集・追加・削除と、完了チェックの復元を対象にする。

### 分割と公開

- URLとデザインを維持し、画像は同じバイト列のまま外部化する。
- 画像、CSS、JSには内容ハッシュを含むURLを用い、日次更新によるキャッシュ混在を避ける。
- 暗号化ペイロードも世代ごとに分離する。個人情報を初期データJSへ平文で出さない。
- 既存関数を責務単位で順に移す。大規模なフレームワーク導入や全面書き換えはしない。
- 公開成果物に対応するソース・テストをGitで管理する。OAuth・トークン・_workの平文は含めない。
- 公開時は参照される全ファイルを検証する。参照関係、ハッシュ、復号、平文漏洩、ルート404を検査し、旧版一式へ戻せるようにする。

## テスト方針

- 初回表示、編集、保存、ページインスタンス作り直しによるリロード、閉じて再開した後の復元。
- 人物追加、既存のイベント削除、シート側の人物削除の同期。
- 最新取得失敗時でも保存済みキャッシュを復元。保存できなかった操作を成功と表示しない。
- JSON破損、暗号文破損、旧形式、不正型、localStorage読書き失敗、容量不足。
- 空欄への変更、行ズレ、重複応答、二重追加、部分失敗、保存中の古い取得応答。
- チェックを付ける・外す・未送信で閉じる・リロード・再送・別端末との同期。
- 一覧、庭、検索、並び替え、フィルター、一括編集、履歴、イベント、カレンダー、分析、モバイル、ロック。
- 既存テストを各段階で実行。実行日の相対日付を使い、時間が経つと壊れるテストを増やさない。
- 実ブラウザE2Eは架空データとAPIモックで実施。本番データをテスト用に追加・削除しない。
- 同じ画像・画面幅で改修前後のスクリーンショットと性能を比較。初期ロード、JS実行・復号・描画、DOM数、転送サイズを分けて記録する。
- 公開検証は複数ファイルの取得・ハッシュ一致・復号・平文漏洩検査とルート404を含める。

## 実装前の確認

この案では、Google Sheetsを正本として維持し、暗号化した端末キャッシュでリロード時の復元を補強する。外部ファイルへの分割は、現行の「comlist.htmlだけを公開」という制約を今回の改修に合わせて変更する。既存の削除操作は残し、人物の削除操作は新設しない。

利用者の指示どおり、分析と改修案の確認を待ってから実装へ進む。
